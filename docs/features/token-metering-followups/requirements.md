# Requirements: token-metering follow-ups

Seven issues found in a holistic review of the shipped token-metering feature (`docs/features/token-metering/` — design docs; code in `tools/tokens/` (vendored, this repo) and `token-metering/` (submodule, backend copy + `frontend/`)). None of these were caught by the feature's own milestone gates (`GOAL-CONDITION.md`'s per-milestone gates all pass); they surfaced only once the feature was exercised holistically, live. This doc and its `specs/` are documentation-only — no fix lands here.

All file:line references below were checked against the code at the time of writing (2026-09-02, `tools/tokens/` and `token-metering/` at their current `HEAD`); a future reader implementing off this doc should re-check them, since the code may have moved since.

## Problem

1. **Ghost projects never expire.** `discover_projects()` (`tools/tokens/server.py:97-127`, byte-identical in `token-metering/server.py`) reads every path listed in `~/.claude/cairn/known-projects.json` unconditionally and turns each into a `Project` label — it never checks whether the path still exists on disk. `hooks/stop-tokens.sh` (lines 46-50) only ever appends to that file, never removes an entry. A worktree that's since been torn down (a normal `EnterWorktree`/`ExitWorktree` cairn workflow) leaves a permanent "ghost" label with zero data behind in the Projects panel (`token-metering/frontend/src/components/ProjectsPanel.tsx`) and the session filter pills, cluttering both forever.

2. **Two frontend overflow bugs, confirmed live.**
   - (a) `token-metering/frontend/src/components/SessionDrilldown.tsx`'s agent-row grid (`grid-cols-[18px_110px_1fr_90px_90px_70px]`, line 82) fixes the name column at 110px. A subagent name like `cairn:planner`/`cairn:builder` plus its "subagent" badge (lines 89-96) overflows past 110px with no truncation, spilling visually into the adjacent token-bar column. The short `main` case (no badge) fits fine today, which is why this wasn't caught earlier.
   - (b) `token-metering/frontend/src/components/HbarList.tsx` renders every row it's given with no cap — confirmed live with 20 unbounded rows in the "Tool calls" panel (`Dashboard.tsx:131-137`). The same unbounded component backs the agent/skill/model/tool/MCP-server panels (`Dashboard.tsx:94-146`), so any of them can grow past what the panel's fixed layout was designed to hold.

3. **Two unbounded full-table scans, no indexes anywhere.** `TokenMeteringApp.session_trace()` (`tools/tokens/server.py:700-703`) and `call_detail()` (lines 705-712) both call `self._fetch_calls(projects)` with no `since`/`until`, unlike every other rollup method in the class (`_ranged_calls`/`timeseries`/`sessions`, etc.), which all bound their query. Each of these two scans every row ever captured in `calls` and filters to one `session_id` in Python. `tools/tokens/db.py`'s three tables (`calls`, `usage_limit_events`, `tool_uses`) declare no indexes at all — not on `session_id`, not on `timestamp`. Not an active bug at current scale (~5k rows, sub-30ms per the review), but there's no rotation, pagination, or archiving in the design, so it degrades as history accumulates with no built-in ceiling.

4. **Duplicated sort is a silent-breakage risk.** `SessionDrilldown.tsx` (lines 27-31) re-sorts and re-numbers every call in a session client-side (`sort by timestamp, then request_id`) purely to compute the `n` position it passes to `onOpenCall` for deep-linking to `/api/call/<session>/<n>`. This exactly duplicates `call_detail()`'s own sort (`tools/tokens/server.py:710`: `calls.sort(key=lambda r: (r["timestamp"], r["request_id"]))`). Nothing enforces the two stay in lockstep — a future change to one sort key and not the other silently breaks the detail-toggle's deep link (it would open the wrong call, not error).

5. **Times render in UTC, not the viewer's local time.** `token-metering/frontend/src/lib/format.ts`'s `formatTimeOfDay` (lines 17-22) and `formatStarted` (lines 30-34) slice the raw UTC ISO string directly, by explicit design (per the file's own comment) to keep tests' seeded UTC timestamps trivially comparable against rendered output. `ActivityHeatmap.tsx` (lines 24-26) buckets its 7×24 grid the same way, off `/api/heatmap`'s day-of-week/hour-of-day fields, which `rollup_heatmap()` (`tools/tokens/server.py:309-324`) computes from `datetime.fromisoformat(row["timestamp"]).weekday()`/`.hour` — also UTC, never localized. A non-UTC viewer's "activity by hour" heatmap and every rendered timestamp are offset from their actual local working hours.

6. **Vendored and submodule copies can drift with nothing to catch it.** Per commit `0779172`'s vendoring (`docs/tasks/vendor-token-metering-backend/`), `tools/tokens/{db.py,parser.py,pricing.py,server.py,prices.json,test_db.py,test_parser.py,test_pricing.py,test_server.py}` are byte-identical to their `token-metering/` counterparts today — confirmed on disk at time of writing. `docs/tasks/vendor-token-metering-backend/plan.md`'s Decision 2 explicitly leaves the `token-metering/` copies "frozen" (kept only to serve that repo's own frontend e2e fixtures) rather than deleting them, meaning both copies are expected to go on existing side by side indefinitely. Nothing — no test, no CI step — checks that they stay identical; a change landing in one and not the other goes unnoticed until someone happens to diff them.

7. **`03-architecture.md` still describes the pre-vendoring layout.** `docs/features/token-metering/03-architecture.md` line 7 states "`db.py`, `parser.py`, `pricing.py`, `server.py`, and `frontend/` all target the `token-metering` git submodule (`cairn-2.0-token-metering`), not this repo" — untrue since the backend (everything but `frontend/`) was vendored into `tools/tokens/`. The Components table (lines 29-37), Data flow step 3 (line 43), and the Testing section's gate description (line 58) repeat the same now-stale submodule-only framing. Checked against `docs/tasks/vendor-token-metering-backend/plan.md`'s Actionable 3, which explicitly updated `docs/BUILD_BRIEF.md` §B10, `ROADMAP.md`'s header, and `GOAL-CONDITION.md`'s Invariants to reflect the split — and both are in fact updated, confirmed on disk — but `03-architecture.md` is not in that actionable's list. This differs from `ROADMAP.md`'s M1-M6 milestone bodies, which the same plan explicitly calls out to leave alone "as historical record of the original submodule-based build" (`plan.md` Scope section) — `03-architecture.md` is the living design description, not a dated log, so there's no equivalent reason to preserve its stale wording. This reads as a genuine oversight in Actionable 3's file list, not a deliberate choice.

## Goals

1. A worktree or project directory that no longer exists on disk does not appear in the Projects panel or the session filter pills, without needing any manual cleanup step.
2. (a) A subagent name plus its "subagent" badge never visually overflows the agent-row grid in `SessionDrilldown.tsx`, for any name length reasonably expected in practice (cairn's own agent names, or a project's custom agent names), while the plain `main` row's layout is unchanged. (b) `HbarList` cannot render an unbounded number of rows — past some cap, the remainder collapses into a "+N more" (or equivalent) indicator, consistent with the component's existing visual style, applied uniformly to every panel that uses it.
3. `session_trace()` and `call_detail()` no longer perform a full unbounded table scan to serve one session's calls. `calls.session_id` (and any column `usage_limit_events`/`tool_uses` lookups actually filter or join on) has a supporting index. The fix holds at today's scale and doesn't regress correctness (same rows returned, same ordering).
4. The client no longer computes its own copy of `call_detail()`'s chronological sort to determine a call's deep-link position — that position comes from the server, with exactly one place responsible for the ordering.
5. Every user-facing rendering of a timestamp (trace rows, session start/end, the activity heatmap's bucketing) reflects the viewer's local time zone, not UTC, while `format.ts`'s and `ActivityHeatmap.tsx`'s tests remain able to assert against fixed, non-flaky expected values.
6. A change to `db.py`/`parser.py`/`pricing.py`/`server.py`/`prices.json` (or their tests) landing in exactly one of `tools/tokens/` or `token-metering/` is caught automatically, before merge, rather than discovered later by inspection.
7. `03-architecture.md` accurately describes where the backend code lives today (`tools/tokens/` in this repo) and where only `frontend/` still lives (the `token-metering` submodule, maintainers-only), matching the correction already made in `BUILD_BRIEF.md`, `ROADMAP.md`, and `GOAL-CONDITION.md`.

## Non-goals

- Implementing any of the seven fixes in this pass — this doc and its `specs/` are documentation only.
- A general project/worktree-lifecycle tracking system — issue 1's fix is scoped to what the dashboard displays, not to teaching cairn's worktree workflow to notify token-metering when a worktree is torn down (unless a spec concludes that's the simpler shape, per its own tradeoff analysis).
- Query pagination, rotation, or archival of `tokens.db`'s history — issue 3 is scoped to bounding two specific unbounded queries and adding indexes, not to a general data-lifecycle redesign.
- Redesigning `HbarList` or `SessionDrilldown.tsx`'s visual language beyond what's needed to fix the two overflow cases in issue 2.
- Changing where pricing, rollups, or any other read-time computation happens — issue 4 only removes the one duplicated sort.
- Any change to `tools/tokens/`'s zero-pip-dependency, stdlib-only constraint (issues 3 and 6) or to the frontend's existing dependency set (issues 2, 4, 5).
- Reconciling the broader question of whether `tools/tokens/` and `token-metering/`'s backend copy should eventually be de-duplicated into one physical source (e.g. deleting the frozen submodule copy) — `plan.md`'s Decision 2 already treats that as a separate, out-of-band, different-repo-access action; issue 6 only adds a drift guard on top of today's two-copies-by-design state.

## Constraints & assumptions

- `tools/tokens/` is gated by `python tools/budget.py` and `python -m pytest tools/` (this repo's own gates); `token-metering/` is gated by its own `.harness/workflow.md` (`pytest`, `npm run build`/`playwright` for `frontend/`) — any spec touching both sides must satisfy both gates independently, per `03-architecture.md`'s existing split.
- `tools/tokens/` stays stdlib-only Python (`03-architecture.md`'s Serving side); `token-metering/`'s backend copy inherits the same constraint since it's meant to stay byte-identical (issue 6).
- The frontend stack is fixed: React 19 + Vite + Tailwind + shadcn/ui components copied into source + `@tanstack/react-query` (`03-architecture.md`'s Serving side) — issues 2, 4, and 5 work within that stack, not by introducing a new library.
- `format.ts`'s UTC-rendering choice (issue 5) was a deliberate test-simplicity tradeoff at build time, not an oversight — its comment says so directly. Any fix has to solve for the same test-simplicity goal by another means (e.g. asserting against a fixed time zone, or computing expected local time from the seeded UTC value), not merely revert the comment's reasoning.
- Capture stays advisory-only and pricing stays read-time-only (`GOAL-CONDITION.md`'s Invariants) — no spec here should touch either invariant.
- All seven issues were found via a holistic review pass rather than a specific bug report; none has a reproduction beyond what's described above (issue 2b's 20-row case and issue 3's ~5k-row/sub-30ms figures are the only measured data points).

## Open questions

- **Issue 1 — read-time pruning vs. write-time GC.** Read-time pruning (skip a `known-projects.json` entry whose path no longer exists when `discover_projects()` builds the project list) is simpler and needs no hook into worktree teardown, so it's the likely default — but it means the JSON file itself never shrinks, only what's displayed; a machine with many torn-down worktrees over time accumulates a permanently-growing file even though the UI stays clean. A write-time GC (something removes the entry when a worktree goes away) avoids that but requires hooking `ExitWorktree` or an equivalent teardown point, which `hooks/stop-tokens.sh` does not currently observe. Left to `specs/01-ghost-project-cleanup.md` to resolve or carry forward as an explicit tradeoff.
- **Issue 3 — exact bounding strategy.** Whether to bound `session_trace()`/`call_detail()`'s queries by the session's own known time range (sessions already have a start/end from the sessions rollup, per the issue description) versus some other bound, and which exact columns need indexes beyond `calls.session_id`, is left to `specs/03-query-bounding-and-indexes.md`.

## Success criteria

1. A worktree removed via cairn's normal teardown no longer appears anywhere in the dashboard (Projects panel, session filter pills) the next time the dashboard is loaded — confirmed by removing a worktree with captured data and reloading.
2. (a) A session containing a subagent with a long name (e.g. `cairn:planner`) renders its agent row with the name and badge fully visible, not overlapping the token-bar column — confirmed visually. (b) A rollup panel fed more rows than its cap shows the cap's worth of rows plus a "+N more" indicator, and no more.
3. `session_trace()` and `call_detail()` return identical results to today's implementation (same session's calls, same ordering) while no longer scanning the full `calls` table to do it; `EXPLAIN QUERY PLAN` (or equivalent) shows the new index is used.
4. Deleting `SessionDrilldown.tsx`'s local sort-and-renumber block does not change which call opens when a trace row's detail toggle is clicked, for any session with multiple agents and multiple calls per agent.
5. A trace row's rendered time, a session's started/ended times, and the activity heatmap's bucketing all reflect the browser's local time zone when the dashboard is loaded from a non-UTC time zone; `format.ts`'s and `ActivityHeatmap.tsx`'s existing test suites still pass, asserting against explicit, non-flaky expected values.
6. Intentionally editing one of the nine vendored files in only one of `tools/tokens/` or `token-metering/` causes a test or CI check to fail, naming the mismatched file.
7. `03-architecture.md` no longer states that backend code targets the `token-metering` submodule; a reader following only `03-architecture.md` and `docs/tasks/vendor-token-metering-backend/` arrives at the same, correct understanding of where the code lives.
